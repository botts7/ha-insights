    Companion app feature request — drafts for github issues¶

    Drafted 2026-05-18 to support HA Insights "Find My HA Device" feature (card v1.10.8 / integration v1.12.18). Copy/paste into the respective companion-app repos.

    File at: https://github.com/home-assistant/iOS/issues/new AND https://github.com/home-assistant/android/issues/new¶

    Title: Feature request: opt-in active BLE scanner with on-demand RSSI streaming

    Body:

    Summary¶

    Add an opt-in, on-demand BLE active-scan mode to the Companion app that streams per-device RSSI back to Home Assistant via WebSocket while a subscription is active. The intent is to turn the user's phone into a temporary mobile BLE receiver so HA integrations (and future HA core features) can offer "warmer / colder" proximity-find UX for any BLE-advertising device known to HA — without depending on stationary Bluetooth proxies.

    Motivation¶

    Home Assistant currently has scattered identification primitives:

    • light.flash service (lights only, single-fire)
    • Companion app "Ring my phone" (mobile_app only)
    • Stationary Bluetooth proxies (ESPHome bluetooth_proxy, Shelly H&T, etc.) — fixed in one room each

    Stationary proxies enable room-level localisation (compare per-proxy RSSI → "device is closer to the kitchen proxy than the lounge proxy"), but they cannot enable warmer / colder UX because they don't move. Users who want to physically locate a misnamed Zigbee bulb (light.0x0015abcd...) or a re-paired smart switch with a cryptic id have no good tool today.

    The phone is the obvious mobile scanner: users already carry it everywhere, and the Companion app already has Bluetooth permission for its passive presence-advertising feature.

    Real-world precedent in the HA community is the "BLE Find My Device" workflow that HA Insights (https://github.com/botts7/ha-insights) attempted to ship: the modal currently degrades to room-level only because there's no mobile-scanner data source.

    Proposed API¶

    A new WS command subscribed by HA, served by the Companion app (reverse direction from current Companion → HA pattern):

    {
  "type": "mobile_app/active_ble_scan",
  "duration_seconds": 60,      // capped at ~120 server-side
  "target_addresses": [        // optional filter; empty = all nearby
    "AA:BB:CC:DD:EE:FF"
  ]
}

    Server (Companion) streams events:

    {
  "device_address": "AA:BB:CC:DD:EE:FF",
  "rssi_raw": -67,
  "rssi_smoothed": -65,
  "name": "Hue White E27",     // when in advertisement
  "received_at": 1716230000.123
}

    Subscription auto-tears down at duration_seconds OR when consumer unsubscribes.

    UX requirements¶

    • Opt-in: a single setting (Settings → Companion → Allow active BLE scan: off by default) gates the entire feature. App must NOT scan in background without consent.
    • Foreground indicator: while scanning, show a persistent notification on the phone ("HA is using your Bluetooth to find a device"). Tap to cancel.
    • Battery-aware: short default duration (60s), hard cap (120s), explicit user dismissal on every session. No "always-on" mode.
    • Permission flow: standard OS BLE permission request the first time; clear messaging that the data goes ONLY to the user's own Home Assistant instance (already paired via the existing companion link).
    • Sub-cycle stop: an explicit "Stop scanning now" button in the panel notification kills the scan immediately, regardless of remaining duration.

    Alternatives considered¶

    1. Stationary proxy network only: works for room-level, doesn't address warmer/colder ask.
    2. One-shot scan service (mobile_app/scan_ble_once — fire-and-return): simpler, but loses the live trend UX users expect from "Find My iPhone."
    3. Web Bluetooth API in the HA Web UI: limited platform support (Chrome only, requires HTTPS + user gesture), no background mode. Companion app is the more portable seam.

    Reference implementation¶

    HA Insights provides: - lib/ble_capability.py — capability matrix for which entities are BLE-trackable - home_insights/ble_live_find WS subscription — consumes per-scanner RSSI from stationary proxies today; would extend to consume from Companion when the feature lands - Card-side BLE-find modal — already renders per-scanner RSSI + trend arrow; would add "Use phone scanner" toggle when companion advertises this capability

    I'm happy to prototype this in a Companion fork if maintainers signal interest. Posting as a feature request first to make sure the architectural direction is welcomed before investing the implementation time.

    Companion-app capability advertisement¶

    Once shipped, the Companion app should advertise the capability via existing config endpoints so HA integrations can detect it. Suggested addition to mobile_app/get_config response:

    {
  "bluetooth_active_scan": {
    "available": true,
    "consent_granted": false,
    "max_duration_seconds": 120
  }
}

    This lets HA-side consumers (HA Insights, future HA-core "Find My Device") gracefully degrade when the capability is absent or consent is denied.

    Followup: HA core service proposal¶

    After Companion lands the feature, file a separate proposal at https://github.com/home-assistant/architecture/discussions/new to add a homeassistant.find_entity_physically service that abstracts: - light.* → flash - switch.* → toggle - media_player.* → chime - BLE-trackable entities → use stationary proxies + Companion active scan if available - Returns capability fingerprint to UI consumers

    HA Insights' lib/identify_capability.py is the prototype for the dispatch layer.
